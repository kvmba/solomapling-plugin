# Release notes — SoloMapling Plugin (SPI)

## 0.4.0-SNAPSHOT

### Fixes
- **隐身术 is now a first-class bot hide aura, and both hide auras actually protect the bot (隐身术 / 橡木伪装 持续期间完全免受怪物攻击).** Two corrections to the previous state-bound-aura work:
  - **飞侠隐身术 (Rogue.DARK_SIGHT 4001003 / NightWalker.DARK_SIGHT 14001003) was wrongly excluded from the buff registry** on the rationale that "hiding a bot from players defeats the point". That was a category error with GM hide: the v83 client renders Dark Sight as a semi-transparent shade and the sprite STAYS on the map — players still see the bot. The registry now includes it for the whole thief lineage (`Job.THIEF`, so 刺客/侠盗/隐士/夜行者/独行客/盗贼 all inherit), its aura frame mirrors the host's own `isDs()` branch (generic `GIVE_FOREIGN_BUFF` with the DARKSIGHT statup normalised to 0, exactly what observing clients receive for a real player), and `BotAuraState` tracks it as a state-bound aura alongside 橡木伪装. `cancelDisguiseForAction` is generalised into `cancelHidesForAction`: an attack drops BOTH hides (the official client cancels 橡木伪装 on the attack key; the host's own damage handlers drop DARKSIGHT on any swing), a mount clears both, and the despawn cleanup covers both.
  - **Neither hide ever granted any protection.** The bot damage path is plugin-owned (headless bots never send TAKE_DAMAGE, so the engine's own hidden-player gating in `TakeDamageHandler` never runs for them), and `BotContactDamage` never consulted any buff state: a bot under 隐身术 or 橡木桶伪装 took touch damage, mob debuffs, fall damage and even touch-retaliated normally. Now `BotContactDamage.tickMobDamage` and `applyFallDamage` short-circuit on `BotAuraState.isMonsterImmune(bot)`: while a hide is shown the bot is invisible to monsters — no contact hit, no mob debuff roll (the disease scan lives in the same gated path), no fall damage, no charged-brawler touch retaliation (官方技能描述: "Can't be attacked, and can't attack either"). The hurt i-frame window keeps ageing while hidden so it never resumes stale after the hide drops, and the swept touch box keeps refreshing so a long hidden stretch cannot leave a stale sweep. 变身 (TRANSFORMATION) morphs deliberately do NOT count — they are attackable and never protected.
  - **Every attack site now provably cancels the hides.** The cancel was already on `BotAttack.basicSwing/skillSwing/rangedSwing/magicSwing` and `BotAttackDriver.attack`; the audit found two real attack types that broadcast without it and both are fixed: the Energy-charge touch retaliation (`BotEnergyCharge.strike` → `bodyStrike` — the narrow cross-thread edge where a cast lands between the contact scan and the strike) and `PqActions.hitReactor` (the PQ stage scripts hit reactors directly with no swing packet; the OPQ path already swung first via `basicSwing`). Summon strikes are exempt by rule — the summon attacks, not the bot, no summon-owning line (archer/mage/DK/pirate-turret) can hold a hide aura, and the official client does not cancel a player's hide when the summon strikes. New `HideCancelAuditTest` pins the whole rule source-level: every swing site in the plugin must carry the cancel, and the damage layer must gate on `isMonsterImmune` in both entry points, so a future attack path cannot ship without it. `BotAuraStateTest` pins the new hide-family classification (橡木伪装 + 隐身术 = the cancelable, protective pair; 变身 never). Two follow-on rules close the loop: death drops the hides (`BotDeath.markDown` cancels them — both death paths flow through it — so a bot that died hidden no longer stands back up still immune), and the hurt i-frame keeps ageing while hidden so it never resumes stale. `mvn test`: 1283 pass (4 new).
- **Bots no longer bounce in place on the Eos Tower's small platforms and never make the jump to the platform beside it (玩具塔「原地蹦跳」).** A JUMP edge's launch window only bounds *where* the bot may take off; it does not promise the arc from every pixel inside the executor's phase band actually clears to the edge's target. Execution fires whenever the bot is within one walk step of the selected launch x (`isWithinJumpLaunchWindow` tolerates the ±walkStep launch phase), and the graph builder's window inset collapses a window too thin to inset to a single pixel (`insetJumpLaunchWindow`) — so the phase band reaches a pixel the builder never validated. On the tower's stacked mini-platforms that pixel's arc comes down on the *source* platform: the bot jumps, lands where it started, walks back in, fires again, and pogoes forever until the travel/grind watchdog warps it away (the reported "站在小平台上原地上下蹦跳，跳不到旁边的平台，最后被系统带走"). `canExecuteJumpFromCurrentPosition` now re-runs the builder's own flight predicate from the bot's live pixel (`BotNavigationGraphProvider.jumpArcReachesTarget`) and withholds the launch unless that arc lands in the edge's target region — so execution can only fire an arc the builder would have accepted. For a window wide enough to inset this is redundant (the band equals the validated span); it bites only on the collapsed windows that caused the bounce. Replayed across all 22 tower floors: stuck jump-cases fall 89 → 58, arrived rises 3897 → 3928, and no floor regresses. `mvn test`: 1274 pass (6 new in `JumpArcReachTest`, which pins the accept/reject rule on the landing).
- **Party-quest bots now actually enter the quest, and stand in the lobby like people.** Two separate defects, reported together as "the bot won't walk or talk in the lobby, and won't follow the party into the quest map":
  - **The bot was never registered in the instance.** `EventInstanceManager.registerPlayer` gates on `Character.isLoggedInWorld()`, which is `isLoggedIn() && !isAwayFromWorld()` — and a template-cloned bot's `Character.loggedIn` is *false by design*: `CharacterService.loadCharFromDB(cid, client, false)` takes the `!channelServer` early return before its `setLoggedIn(true)` (that same early return is what keeps the hourly autosaver from writing thousands of ambient bots to the database). The plugin only ever called `markPresentInWorld()`, which clears `awayFromWorld` and nothing else. So a bot in the party was silently dropped: no `setEventInstance`, no `playerEntry` warp, absent from `getPlayerCount()` — which means every body-count puzzle (Kerning's ropes/platforms, Orbis's three-platform stage, Ludi's crates) could never be satisfied. The host now admits artificial characters through the same `HostHooks.isArtificial` check every other reachability gate already uses (`MapleMap`, `Monster`, `PlayerShop`), and the symmetric `exitPlayer` gate was widened to match so a bot that leaves is unregistered instead of lingering in `chars` forever. The rules are extracted as `admitsParticipant` / `admitsLeaver` over primitives precisely because the previous "verified by reading the source" form was untestable — `Character` cannot be constructed in a unit test — which is how this shipped broken in the first place. Host change: `EventInstanceManager` (2 call sites), plus `EventInstanceManagerAdmissionTest`.
  - **The bots had no lobby behaviour at all, and no lines to say.** `PartyQuestBot.tickPartyQuest` returned the moment a bot was outside the quest, so a recruit-lobby crowd was a set of statues that ignored being talked to. The shared skeleton now spends the wait the way the long-standing Orbis bot does: a recruit shout naming its own quest (new `PqRecruitMessages` + `pq.recruit.name.*` in both message packs, using each quest's own in-game name — 迎月花山丘 / 第一伴奏 / 时空裂缝 / 海盗船 / 阿莫利亚挑战 / 毒雾森林 / 罗密欧与朱丽叶 / 扎昆战役 / 暴君蛋龙试炼场 / 首领突袭 …) and a stroll to a fresh spot on the lobby floor, both deadline-jittered so a spawned cohort does not shout in lockstep, both gated on the map actually being watched. Bots also answer now: `respondsToSocialChat()` (greetings, via the existing social-reply path) and `offerRecruit()` (an open "anyone want to party?" shout, via the shared accept/decline roll). Before this, a quest bot's `dialoguePath` pointed at a YAML file that does not exist, and all three social hooks were the silent defaults.
  - **The follow-the-leader step picked the wrong door.** `followLeaderIntoNextRoom` walked onto the nearest portal, and in a real quest room that is almost always the spawn point (`sp`, target `999999999` — the engine's "no map" sentinel) or a return portal. It now selects the portal whose *target* is the room the leader is in, and enters it through the portal script, so the quest's own stage gate still decides whether passage is allowed. Pinned by `PartyQuestPortalChoiceTest` against the engine's portal type.
  - **Going home had to be re-done for a bot that is now really registered.** `returnToLobby` warps the bot back to town, and two engine details only bite once a bot is in an instance: `Character.changeMap` re-resolves through `getWarpMap`, which answers with the *instance's* copy of a map while an instance is set (an empty ghost town nobody can see), and the lobby must be resolved on the bot's **own** channel. The warp now unregisters first — exactly what the quests' own `playerExit` does — then resolves the lobby through the bot's client. `OrbisPQBot` gained the same `unregisterPlayer` on its way back to its lobby, since it is registered now too. `mvn test`: 1268 pass (8 new).

- **State-bound bot auras now follow their real rules (疾驰 / 橡木伪装).** A bot's buffs are cosmetic broadcasts, so the movement/pose rules the official client enforces itself were missing. Two auras are not simply duration-bound, and both are now governed:
  - **Pirate 疾驰 (DASH, e.g. 5001005)** is a speed/jump burst the player holds only while WALKING — the double-tap starts it and it drops the instant the player stops, jumps, swims or grabs a rope. The plugin's aura packet carries a fixed duration, so it used to linger through every stand / jump / swim / climb. New `BotAuraState` resolves whether a bot's kit carries a 疾驰 (from its job's buff registry, cached) and the movement tick now OWNS the display: it shows the aura while the bot's wire stance is a walk (refreshed on the aura's own WZ cadence) and cancels it on the very next Stand / Jump / Swim / Rope / Ladder stance. `BotBuffDriver`'s periodic sweep and `BotFlavor`'s buff-flex both now skip 疾驰 so it is never cast from a stand (where it would read as a lingering aura).
  - **Pirate 橡木伪装 (OAK_BARREL, 5101007)** is a hide morph. In the official client the attack key's handler cancels it before doing anything else (`if (IsHideMorphed()) SendSkillCancelRequest(BRAWLER_OAK_BARREL)`), and taking a 骑宠 mount clears it. Bots now do the same: `cancelDisguiseForAction` runs at every swing site (`BotAttack.basicSwing` / `skillSwing` / `rangedSwing` / `magicSwing`, `BotAttackDriver`, and the summon's own context) alongside the mount's existing `cancelForAction`, and the movement tick retires it while a mount is up. The 变身 (TRANSFORMATION / SUPER_TRANSFORMATION) morphs are ATTACKABLE, so they are tracked separately and the attack rule cancels ONLY 橡木伪装 — never a 变身.
  - New `BotAuraStateTest` pins the pure rules (疾驰 holds only on a walk stance; only 橡木伪装 is the censorable disguise; the 变身 family is distinct) and `BotBuffEffectsLayoutTest` cross-checks the dash skill-id set (now single-sourced in `BotAuraState`) against the host `StatEffect` predicates.
- **Bot summons now hover beside the bot with a small float (the official look), not a slow wide orbit.** The summon follower previously orbited the owner on a 70px ring (hawks/eagles/dragon) or hovered at a far offset — neither matches the client, where a flying summon (hawk / eagle / phoenix / frost-prey / elemental / dragon / bahamut / beholder) simply floats just beside the owner with a tiny bob, exactly like a pet. The follower now glides every non-stationary summon at a bounded speed (never warping) toward a slot ~60px in front of the owner's facing and ~65px above, perturbed by a small per-summon sine bob (14px x / 8px y, de-synced by a random phase). The spawn `nMoveAbility` byte is left exactly as the host sends it (archer birds `CIRCLE_FOLLOW`=3, the mage/beholder/bahamut line `FOLLOW`=1) — the client reads that byte for its initial-action fallback, so it stays a parity fact; only the server-authored movement changed. `BotSummonConfig`'s `move` section is re-keyed to the hover model (`offset_x`, `offset_y` with the original negative-is-up convention, `bob_x`, `bob_y`, `follow_speed_x`, `follow_speed_y`, `tick_ms`, `snap_distance`); existing configs keep working, the section is optional. `BotSummonMoveRuleTest` now pins the hover slot and the bob bound; `BotSummonTableTest` pins the host-parity move bytes and `BotSummonConfigTest` follows the new keys.
- **Bot buffs that the v83 client decodes with extended frames no longer crash observers (「数据过短」).** Not every buff travels through the generic `GIVE_FOREIGN_BUFF` frame: the host's own `StatEffect.applyTo` routes three skill families through *extended* frames the client reads with extra fields — pirate 疾驰 (`isDash()`), 极速领域 (`isInfusion()`, incl. 5221010 which the host names `Corsair.HEROS_WILL`), and the `WK_CHARGE` 元素剑 family (`isWkCharge()`). The bot buff path broadcast everything through the short generic frame, so the client parsed past the end of the packet and crashed (the reported "data too short" symptom) — and 疾驰, 极速领域 and 勇士的意志 were exactly the skills the expanded registry had just added. `BotBuffEffects.broadcastAura` now mirrors the host's dispatch: the two pirate families (疾驰 / 极速领域 5121009·15111005·5221010) go through `giveForeignPirateBuff` (per-stat value + skill id + skip + duration, seconds), the charge family (烈焰/寒冰/雷电/圣灵之剑) through `giveForeignWKChargeEffect`, and every other buff keeps the generic frame. The same dispatch applies to a GM-granted buff (`giveExtendedBuff`), whose custom length is what the pirate frame carries. New `BotBuffEffectsLayoutTest` cross-checks every dispatched skill id against the host `StatEffect` predicates, so a host-side change cannot silently un-mirror the plugin. `mvn test`: 1264 pass.
- **Bot summons are now moved and fought by the server (they used to stand frozen at their spawn point).** A client only drives the summon it owns - the local player's own. Every other summon, a bot's included, is rendered by observers purely from the `MOVE_SUMMON` frames the server relays: for a real player the owner's client produces those frames and the host merely echoes them, but a headless bot has no client to produce them, so the previous "the client animates the follow/orbit from the spawn movementType" reading left every bot summon parked at its spawn point while the bot fought across the map. `BotSummonFollower` now plays the client's part, the same way the pet system already does in-game:
  - One shared 300ms tick computes each hovering summon's slot (a small offset in front of the owner's facing with a tiny bob - see the hover fix above) and broadcasts a `MOVE_SUMMON` frame carrying one absolute-move fragment - byte-for-byte the layout the host relays for a real player (`AbsoluteLifeMovement` serialisation: `[cid][oid][startPos][count=1][type 0 | x y | vx vy | fh | action | duration]`).
  - STATIONARY summons (the pirate turrets) are never repositioned and never receive a movement frame; they sit exactly where they spawned.
  - LOD matches the rest of the bot layer: on an unobserved map the tick still advances each summon's slot in memory (cheap arithmetic, no packets) so a player arriving sees it in place rather than at a stale spawn point, and only the observed map broadcasts frames.
  - Lifecycle is leak-free and race-free: a bot that vanishes without the normal remove hook has its plugin-owned entities torn down by the tick (and by shutdown even when the character can no longer be looked up), a summon whose (re)spawn failed is retried while it is still tracked instead of being skipped forever, and the register/teardown paths share one lifecycle lock so an in-flight tick can never re-spawn a summon that a concurrent despawn just retired (no ghosts), nor observe a list mid-append.
  - An owner who teleported (> `snap_distance`, default 900px) re-seats the summon at its slot with one same-point frame instead of gliding it across the map.
  - `BotSummonConfig` regains the `move` section (`tick_ms`, the hover offsets, the bob amplitudes, the glide speeds, `snap_distance`); existing configs keep working, the section is optional.
  - New tests: `BotSummonMovePacketTest` pins the frame bytes, `BotSummonMoveRuleTest` pins the turret rule (`shouldReposition`) and the hover maths. `mvn test`: 1258 pass.

- **Bots no longer walk or down-jump off a ledge with no ground below it (the "fell out of the map" glitch on terraced fields).** Some hunting grounds — e.g. 地球防御本部 (EDF, `221030xxx`-`221040xxx`) — are terraces whose every layer is built from many small foothold segments, and each layer's outer end is a void cliff: the column under the end pixel has no foothold at all. Three execution paths could leave the map there and free-fall (the airborne integrator has no floor clamp, so the bot plummets until the fall-off-map recovery snaps it back and clears its goal — the visible "card in the seam, then fell out"): a grounded step that overshoots the lip by the one-pixel intent clamp (the walk gate blocks the normal case, but the clamp lets the executed pixel cross into the void); a straight down-jump (`canStartDownJump` only checks the takeoff ledge's `forbidFallDown`, so a reused/stale DROP edge fired from the landing terrace — the documented "re-fires from the landing platform where there's no lower foothold" case — launched a drop that never landed); and the 500ms stuck-recovery hop, whose random direction could launch outward off the edge. All three now gate on the same landing check the graph builder already uses (`simulateFallLanding` / `simulateJumpLanding` / `simulateDownJumpLanding != null`), so a step or jump that reaches real ground below is untouched. A walk held at the lip clears its held direction and velocity and renders STAND (not a walking-in-place WALK). Verified by replaying the real EDF geometry: out-of-map walk-offs go from 56-140 per map to 0 while the count of real ledge drops is unchanged, and the stuck hop picks the inward direction at a lip. `mvn test`: 1226 pass.
- **Training bots no longer abandon a continent that still has mobs for them.** Continental migration (a bot that "outgrows" its landmass moving to one whose mobs still bite) tested only whether a harder continent's level bar was cleared, and treated any YES as "this one is finished". That is a different question, and the wrong answer drained the low-bar continents: 地球防御本部 (EDF, map `221000000`, inside Ludibrium — bar 30) holds fields for its 40-54 cohort, but a 45-level bot there cleared every harder bar, so it was ordered off on its first town visit. Since a migration only ever relocates to another continent's *town* and EDF is not one, the bot could never return — EDF bled out, with no refill (bots are spawned once, at startup; the real curve depends on how fast the crossings resolve). The climb is now content-aware: `TrainingMapChooser.hasInBandTarget` asks whether a level-appropriate hunting ground is still reachable (the same two-sided band and level-scaled radius DECIDE uses, plus the deep-hub downward floor, and it band-checks the result because the finder's non-empty fallback would otherwise always answer "yes"), and `forcedCrossing` — one shared statement of the rule, used by both the training bot and the companion — forces a move only for a genuine outgrowing or the beginner island's one-way boat. A free mover's move stays optional (the existing 25% dice). Above the free-move level, or when nothing is left to fight, migration behaves as before; the island's `level 8` boat is deliberately never gated (it is an exit, not a continent to outgrow, and the island holds level-appropriate mobs).
- **Bot names no longer contradict their job.** A bot's IGN and its class were two independent rolls, so a third of the zh-CN names — which lean on role words like 圣骑士 / 大主教 / 魔法师 / 弓箭手 — landed on a bot of a different class (`圣骑士肝帝` walking around as a thief). Names are now drawn to match the job they will get:
  - `BotNamePool` classifies each name by the v83 job category its role word asserts (warrior … pirate), with the flavour words that are not v83 classes (龙神 / 恶魔 / 天使) kept neutral and the town name 勇士部落 subtracted from the warrior word 勇士.
  - Both pools are covered. The English list is the default language; its words match on ASCII token boundaries (`sin`⊄`Since2005`, `mage`⊄`image`), the Chinese list on substrings (no word boundaries in CJK), so the default English world filters names too.
  - `FMShopDescGen.getRandomCharacterIGN(int category)` returns the first name that is neutral or asserts the bot's own category; the plain `getRandomCharacterIGN()` still works for an unknown class.
  - The category is resolved once in `BotGeneration.createBotOn` (from the forced job, else the rolled/known base class) and handed to both the name draw and the decoration, so the name is fixed before the job is rolled and the two can never disagree. The no-class spawn path previously let `BotDecorate` roll its own base class; it now reuses that single roll (same default 10..80 band).
  - Companions are named the same way: intake draws the persona seed first, derives the class from it, and passes the same seed to provisioning, so a companion's IGN matches the career it trains as.
- **Pirate (base class 5) is now a first-class bot job.** Ambient / training bots previously never rolled a pirate (`rollBaseClass` excluded class 5), and a pirate's `getJobStyle()` resolves to `BRAWLER`/`GUNSLINGER` (never `PIRATE`), so any style-keyed lookup silently degraded it to "no job" (reqJob 0). Fixed end to end:
  - `rollBaseClass` now yields pirates at ~10% (after thief > mage > warrior > bowman); `selectJobForClass` covers all four tiers (500 / 510,520 / 511,521 / 512,522).
  - `getReqJobViaJobStyle` maps `BRAWLER`/`GUNSLINGER` → `PIRATE` (reqJob 16), so a pirate can wear its knuckle/gun and pirate armour.
  - Gear selection equips knuckle (brawler) or gun (gunslinger), branched on the job id (the decorator runs before STR/DEX are aligned).
  - Bot combat registers both pirate lines (Double Uppercut / Energy Blast / Barrage; Invisible Shot / Burst Fire / Rapid Fire / Battleship Cannon) plus a 1st-job weapon seed (knuckle melee / gun ranged, like the 1st-job rogue).
  - Bot buffs cover the pirate boosters (2nd), Transformation / Octopus (3rd) and Maple Warrior / Speed Infusion (4th).
  - `!bot spawn ... pirate` and `!bot trainhere <brawler|...|corsair>` are accepted.
  - Free-Market pirate shops now stock pirate gear instead of falling back to classless common items.
  - Pirate attack skills carry their real body-action poses (straight / somersault / doubleupper / eburster / triplefire / cannon / ...), read from the v83 client's own action table.
- **Bot fame was the bot's internal character id.** `BotGeneration` set every artificial player's 人气度 to its own cid (`setFame(botId)`, a debug leftover from the upstream port), so all bots showed a five-digit reputation starting at 20000. Fame is now rolled from level and tier instead (see `BotFame`):
  - low-level bots land around **-10..30** (beginners sit in the low single digits)
  - the ceiling grows with level but never exceeds **300**
  - **~15% of the population carries a negative reputation**
- Fame is generated after the bot's level/tier are final, and re-rolled where a level is overridden post-decoration (OPQ lobby bots, `spawnAttackTestBots`), so reputation always matches the level shown.
- `getConsoleBot` bypasses `BotDecorate`, so it now rolls its own fame instead of inheriting the template character's value.
- New GM commands: `!bot fame <cid>` (inspect), `!bot rerollfame <cid>`, `!bot setfame <cid> <-50..300>`.

### Features

- **Bot detail window (角色详情窗口) is populated.** Opening a bot's character-info window (CUIUserInfo) used to show whatever the `fmbot` template character held — the same empty/duplicated monster book, medal book and wishlist for every bot, because bots inherit the template's `Character` state. The window's packet (`charInfo`) carries exactly three data sets, and all three are now preset per bot at spawn (`soloMapling.ArtificialPlayer.BotDetailSystem`):
  - **怪物卡 (monster book):** book level + normal/special/total counts, scaled by level and replayed through the host's own `calculateLevel()` curve. Only the three private counters are written (reflection; `addCard` would broadcast and dereference a null headless player); the per-card map is not touched (the window never reads it) and the cover stays 0 (an unbacked cover id would NPE `getCardMobId` for every viewer).
  - **勋章收藏 (medal collection):** a deterministic, level-scaled subset of the 28 medal-granting `29xxx` quests marked completed. Eligibility reuses `BotMedalPool.eligibleFor`, so a job-exclusive (29300–29304, reqLevel 180) or too-high-level medal quest can never appear; the worn medal's own quest is always included. Written via `getQuestNAdd(...).setStatus(COMPLETED)` — not `updateQuestStatus`, which would also award fame and emit packets.
  - **心愿单 (wishlist / 想要购买的道具):** a level-scaled subset of the host's on-sale, non-package cash items (≤ the client's 10-entry cap), from a pool cached against the live catalog's identity so a spawn never re-scans ~8k items.
  - All values are derived deterministically from the character id, so a persistent companion shows the same content across restarts; ambient bots are never persisted, so this is pure in-memory state for them. Injected at the same point as `BotMedal` (`BotDecorate.setBotVariables` ×3 paths, `loadPersistentBot`) plus the 5 level/job overrides. The monster-book aggregate is written through a new host API, `MonsterBook.setCardCounts` (the only GMS083 change).
  - New GM commands: `!bot detail <cid>` (inspect) and `!bot rerolldetail <cid>`.
- **Bot titles (称号/medals):** decorated bots roll, level-scaled, for a 称号 and wear it at spawn — no title below level 10, rising to a **50%** ceiling at level 130, with higher-level bots biased toward the fancier (reqLevel > 0) titles. A medal is the v83 `Me`-slot equip (`114xxxx`, slot `-49`), so wearing one is pure inventory state — the host's `addCharInfo` carries it in the look packet and the medal's own stat bonuses apply through the normal equip-stats recalculation. Bot play does not read those stats, so the effect is cosmetic.
  - The legal pool is scanned once from the client `Character.wz` (the host `EquipType` has no MEDAL value, so `EquipMetadataCache` skips medals) and keeps only real, localized (han-character) titles, excluding 人气 / 宠物-intimacy titles.
  - A bot only ever wears a medal it can legally wear (`reqLevel` / `reqJob` / `reqSTR…` / `reqPOP` all satisfied), and the title is re-rolled wherever the level or job is overridden (OPQ lobby, attack-test spawn, `!bot setlevel` / `setjob`).
  - New GM commands: `!bot medal <cid>` (inspect), `!bot givemedal <cid> [itemid]`, `!bot removemedal <cid>`, `!bot rerollmedal <cid>`.
- **SocialBot Hybrid LLM chat:** optional DeepSeek integration for free-form player dialogue during active SocialBot sessions (`solomapling.llm.*`). Menu options, party recruit, and goodbye remain YAML/rule-driven.
- Uses [simple-openai](https://github.com/sashirestela/simple-openai) (`SimpleOpenAIDeepseek`); client + OkHttp/Jackson shaded into the plugin jar.
- `DialogueContextResolver.buildSnapshot()` exports live game context into LLM system prompts.
- **Brawler pirate bots now run 能量获得 (Energy Charge, 5110001) for real.** The skill is entirely client-driven in the host — the bar is charged by the CLOSE_RANGE_ATTACK handler and the retaliation arrives as a `TOUCH_MONSTER_ATTACK` — so a headless bot could never trigger either half. Both are now synthesized in the plugin, reusing the host's own values and packets so onlookers cannot tell (`soloMapling.ArtificialPlayer.BotAttackSystem.BotEnergyCharge`):
  - Each landed swing adds 102 per mob hit, exactly as `Character.handleEnergyChargeGain` does; the bar arms at 10000 and flips to the host's 15000 full value in the same step, so a bot never rests in an armed-but-idle state.
  - Reaching full broadcasts the skill's own charge flash plus the foreign `ENERGY_CHARGE` stat (the bar value, clamped to the client's 10000 gauge ceiling, is what draws the gauge over the bot) and arms a self-expiry at the skill's WZ duration, after which the bar empties and the gauge is cancelled from every viewer — the host's own timer does the same two things.
  - While full, a mob touching the bot takes a real hit (rolled from the bot's tier/level). The touch is its own attack in the v83 protocol — the client sends it as `TOUCH_MONSTER_ATTACK` (`0x2F`, "能量攻击") and the server answers with `ENERGY_ATTACK` (`0xBD`) — so the strike is broadcast on that opcode with the brawler's own punch pose and its damage line, then applied through the same kill/EXP/loot path as every other bot hit. A viewer plays the real strike instead of only watching the mob's HP drop. Cadence is the charged skill's own ~1s attack interval, independent of the bot's hurt i-frames, exactly like a real client.
  - Only the brawler line holds a charge (Marauder 511 / Buccaneer 512 — the jobs the host's own gate covers); the gun line and Thunder Breakers are untouched.
  - Runs entirely inside the existing LOD gates: the charge rides the attack path, and the retaliation reuses the contact tick's own nearby-mob scan (an extra scan only when a charged brawler is actually due to retaliate).
  - New GM commands: `!bot energy <cid>` (inspect the bar), `!bot energycharge <cid>` (fill it now), `!bot energyreset <cid>` (empty it).
  - One new host API, `PacketCreator.energyAttack` (the only GMS083 change, `33ad70ea0`): the `ENERGY_ATTACK` opcode was declared but never built anywhere in the engine, so no touch-triggered attack could be echoed back as a real strike — it had to fall back to a bare damage number. It is the same `addAttackBody` the other three attacks use, behind that header (matching the reference v83 server, where all four share one body). Requires a host build at or after that commit.
  - The charged value lives on the host's own `Character.energyBar`, so the char-info packet renders the charged look with no extra work. The skill is granted before the bar can reach full, at the level the bot's own character level would plausibly hold — 1 on the day of the level-70 third job, filling in at the server's own SP rate (3 a level, 1 a skill level) so a 511 bot reads as maxed from ~83 up. This is not cosmetic-only: Energy Charge's charged state lasts 31s at level 1 and 50s at level 40, so a fixed max grant would have given freshly-advanced bots a duration they never earned. Level below 70 grants nothing and charges nothing. The grant itself is required: the host's `reapplyLocalStats` reads this skill's effect whenever the bar is 15000 and would index `effects[-1]` for an unlearned one, so charging is skipped outright if the skill cannot be resolved.

### Localization

`solomapling.language: zh-CN` previously only switched the bot dialogue packs, so free-market bots kept shouting English lines that were hardcoded in Java or read from English-only word lists. Those three paths now follow the language setting:

- Merchant bot shouts moved from Java string arrays into `MerchantBotDialogue.yaml` (`SellAdvertise`, `BuyAdvertise` with `%ITEM%` / `%PRICE%` placeholders, plus `NXAdvertise` and the NX messenger hand-off nodes).
- Shop names / descriptions resolve through the new `FMNameDesc-zh-CN/` word lists, with the English lists as fallback. Bot IGNs and kaomoji stay ASCII on purpose.
- Remaining hardcoded strings moved into YAML / word lists: the AFK price-update whisper and offer hint (`ShopOfferDialogue.yaml`), the shop greeting (`welcomeDesc.txt`), the offerable tag (`offerableDesc.txt`), and the RWT currency tags (`rwtCurrencyDesc.txt`).

Directory-level language resolution is now shared by `LocalizedResources` instead of living in `DialoguePackPaths`, so any resource pack can gain a `-<tag>` sibling. Shop-title padding also measures rendered width rather than `String.length()`, so double-width names aren't padded as if they were ASCII.
